주요사항

ISSUE 01

복잡한 서비스 로직의 파사드 패턴 대체 방안 및 현실적인 구성의 필요성

🚨 문제 인식

Monolithic 시스템에서 복잡한 채권 체결 및 백오피스 데이터 반영 시 서비스 로직이 비대해지는 상태였으나, 파사드 패턴을 직접 적용하기에는 별도 서비스 승인 작업이 필요하는 등 빠르고 현실적인 대응 방안이 필요하였습니다.

✅ 문제 접근 및 해결 방안

프로젝트가 도메인 영역 별로 엄격하게 분리 운용되고, 서비스 추가 시 승인 절차가 필요하는 등 부가 작업으로 인한 비용 소모가 많았기에 controller가 아닌 service layer에서 부가적인 dto와 mapper 구성 등을 통해 지엽적으로 facade 패턴화하였습니다. 또한 Mybatis 특성 상 JPA와 달리 도메인 객체 내부에서 정책을 적용할 수 없고, 정책 반영이 완료된 값을 mapper로 넘겨주어야 하였습니다. 이때 도메인 정책 반영은 dto의 책임 영역이 아니었기에, service layer 내부에서 정책을 적용하여 상태를 반영할 수 있도록 캡슐화 및 util화를 최대한 적용하여 가독성 및 응집도를 향상하였습니다. service layer 내부에서 적절한 OOP를 적용하여 로직의 흐름을 최대한 구조화하였으며, facade 패턴이 지엽화되고 단일책임원칙(SRP) 준수가 현실적으로 힘든 상황에서 최대한 변경점을 Service layer에 집중하였습니다. 그 결과, 개방폐쇄원칙(SCP) 및 인터페이스 분리원칙(ISP)를 최대한 준수하여 서비스 구조화를 진행할 수 있었습니다.

ISSUE 02

복잡한 서비스 로직의 효율적인 구현 방안

🚨 문제 인식

서비스 로직이 복잡해지면서 Redmine 기반의 단순 테스트 및 결과 비교보다는, 테스트 내역을 객관적으로 정립하고 정량화하여 Service layer를 좀 더 효율적으로 구성할 수 있는 방안이 필요하였습니다.

✅ 문제 접근 및 해결 방안

프로젝트 일정 관리 도구로 사용하였던 Redmine의 경우, 필요 기능에 대한 명세에 집중하였기에 복잡한 서비스 로직의 테스트 커버리지를 명세에 의한 직관성 등 정성적인 요소에 의존하였습니다. 이에, TDD 기반의 테스트 요소 정립 및 기능 개발을 통해 명확하고 객관적인 개발을 진행하기 위한 계획을 수립하였습니다. 시스템 환경 상 Docker TestContainer 기반의 가볍고 독립적인 테스트는 불가능하였으나, Dev 환경에서 Service layer 중심의 단위(Slice) 테스트 및 이를 기반으로 한 기능 구현을 통해 Monolithic 애플리케이션 단위가 아닌 단위 기능 중심의 집중적, 효율적인 개발을 추구하였습니다.

ISSUE 03

Massive Query 작성 시 특정 속성 누락 및 NULL 허용 등으로 인한 복잡도 증가 및 비효율성 문제

🚨 문제 인식

Mybatis native query 작성 시 채권 데이터와 백오피스 데이터의 일부 속성이 없거나, 정책 누락으로 인한 연산 불가 등으로 비효율적인 쿼리 작성 상황이 발생하였습니다.

✅ 문제 접근 및 해결 방안

연산 불가로 인한 쿼리 비효율화가 심하였기에, 특정 속성에 대한 추가 및 default 정책 정립 등 모델링을 개선하여 Massive query의 효율성 및 가독성을 향상할 수 있었습니다. 더불어 비즈니스 로직의 정합성을 service 로직과 데이터베이스 속성 조건 등을 통해 비교적 안정적으로 확보할 수 있었습니다.

ISSUE 04

채권 내역 관리 부하 테스트 시 수정 동시성 문제(Lost Update) 발생

🚨 문제 인식

11~12TPS 상황에서 거래 내역 수정 시 일부 연산이 반영되지 않는 동시성(Lost Update) 문제가 발생하였습니다.

✅ 문제 접근 및 해결 방안

최초 Redis 분산 환경과 체결ID를 활용하여 체결 건의 동시성 방지 및 Request Collapsing을 시도하였습니다. 이후 폐쇄망 환경에서 수용 가능한 대기시간 및 아키텍칭의 복잡도, 데이터 정합성 등을 우선적으로 고려하여 Oracle for update 배타락으로 서비스 로직을 단순화 하였으며, 이에 대한 유지 비용을 절약하였습니다. 여기에 그치지 않고 체결 건 노출 기준을 직급 및 부서 별이 아닌 개인 별 노출로 강화하고 모델링을 개선하는 등 설계적 관점에서 동시성 문제를 접근하여 아키텍칭 비용과 유지 비용을 최소화할 수 있는 개선 방안을 지속적으로 고민하고 적용하였습니다.

ISSUE 05

채권 내역 관리 부하 테스트 시 삽입 동시성 문제(Duplicate Insert) 발생

🚨 문제 인식

11~12TPS 상황에서 거래 내역 삽입 시 Oracle 채번 테이블 기반 동시성(Duplicate Insert) 문제가 발생하였습니다.

✅ 문제 접근 및 해결 방안

채권 체결 최초 등록 시 Oracle 채번 테이블 기반 PK 생성 및 Oracle 격리 수준(Read Committed)으로 인한 PK중복 문제가 발생하였습니다. 최초 비관성 락을 시도하였으나 사용자 경험 측면에서 매우 비효율성을 초래하여, 채번 테이블 모델링 개선을 통해 중복 및 사용자 경험 저해 문제를 개선하는데 기여하였습니다. 모델링 개선의 핵심은, 자연키 기반이지만 max count 산출 범위를 제한적으로 조정하여 동시성 문제를 본질적, 구조적으로 접근하였다는 점입니다. 지속적인 개선점과 비용을 고민하면서 팀에 기여할 수 있었던 경험이었습니다.

ISSUE 06

서로 다른 WAS(채권/경영정보) 환경에서의 세션 정합성 불일치 문제

🚨 문제 인식

채권 서버에서 백오피스(계정) 정보 변경 후 이에 대한 내용이 경영정보에 즉시 반영이 되어야 하였으나(특정 직급 및 부서 별 경영정보 데이터 노출 기준을 차등 적용), WAS가 상이한 환경으로 해당 세션 정보의 즉시 반영이 불가능한 상황이 발생하였습니다.

✅ 문제 접근 및 해결 방안

채권 체결 동시성 문제 해결 시 실무에서 정합성 보장을 우선적으로 고려한 접근을 최초 시도하였습니다. 이때 데이터베이스의 백오피스 데이터를 그대로 활용하고자 하였으나 경영정보에서의 채권 영역 기반의 아키텍칭이 필요하여 이로 인한 복잡도/비용/DB부하 등 side effect가 과도하다고 판단하여, 사 측이 도입한 Redis를 적극 활용하게 되었습니다. 채권 백오피스 정보 변경 후 이 내역을 Redis에 저장하고, 경영정보 측에서 1~5분 주기의 Redis Polling을 통해 세션 정보의 정합성을 최대한 보장할 수 있도록 구현하였습니다. 참고로 경영정보 시스템의 이용 대상이 주로 부장 및 임원급이며 PC off 상태가 빈번하다는 점을 고려하여, stateless한 Redis polling이 Connection 및 자원 점유가 그리 크지 않을 것이라 판단하였습니다. 더불어 Redis Stream 및 Pub/Sub의 경우 대상 Client가 alive하지 않는다는 점과 메시지 유실 문제 등의 부작용이 존재하였기에, 이를 고려한 최선의 데이터 정합성 확보 방안을 적용하였습니다.

ISSUE 07

한국 거래소 데이터 전송 시 단순 순회 기반의 스케쥴러(반복문 방식)으로 인한 반영 누락 결함 발생

🚨 문제 인식

채권 거래 체결 이후 이를 한국 거래소로 반영하기 위한 스케쥴링 처리 시 통신 오류가 발생하여, 반영 누락 결함이 발생하였습니다.

✅ 문제 접근 및 해결 방안

기존 단순 스케쥴링(for 순회 및 row 기반 slice화 기반의 반복 처리) 도중 오류 발생 시 재시도나 fallback 체계가 미흡하였습니다. 따라서 본질적인 개선을 위해 Spring Batch 도입을 시도하였으며, JPA가 아닌 MyBatis 환경이었기에 MybatisPagingItemReader 기반의 chunk Batch 및 재시도 3회 시도 등 최대한 시스템에 부합하는 Batch 로직을 구성하고자 하였습니다. 더불어, Working time이 아닌 새벽 시간에 일어나는 batch임을 고려하여 처리 속도보다 미전송 0건을 달성하는 방향으로 접근하였으며, DB 부하가 충분히 수용할만한 수준임을 확인하고 진행하였습니다. 더불어 단순 통신오류가 아닌 거래소 측 치명적 결함 등 익일 시도가 필요한 체결 내역이 존재함을 고려, 상태변경을 반영한 배치 작업을 시도하는 등 정합성을 확보하기 위한 방안을 적용하여 3일 누적 미전송 결함 0건을 달성하는데 기여할 수 있었습니다.
