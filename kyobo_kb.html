주요사항

ISSUE 01

사전 및 담보 도메인 세부 아키텍칭 누락으로 인한 보일러 플레이트 코드 비대화 발생

🚨 문제 인식

AA팀 주도의 사전 도메인 코드 및 layer 아키텍칭은 완료하였으나, 사소하면서 세부적인 아키텍칭이 부족하여 반복성 코드가 불필요하게 많아지고 있는 상황이 발생하였습니다.

✅ 문제 접근 및 해결 방안

주간 기술리뷰를 주최하여 매주 월요일마다 사전팀에서 자주 사용하는 검증 로직이나 날짜 및 Json stringify 등 사소한 부분까지 반복적으로 발생하는 기능을 정의(패턴화)하였습니다. 이를 기반으로 그 규모에 따라 모듈성, util성, handler로 분리하여 책임을 나누고 이에 따라 캡슐화하는 등 불필요한 중복으로 발생하는 보일러 플레이트 요소들을 상당부 제거하였습니다.
보일러 플레이트 제거의 주안점은 반복성 로직을 최소화하는 것도 있지만, 가장 중요하게 생각하였던 부분은 개방폐쇄원칙(OCP)에 기반한 객체지향성 설계에 기반하여 그 구조를 구현하고 표준화하는 것이었습니다. Java의 본질과 기본에 충실하여 사전 도메인의 클린 아키텍처를 정립하고, 특히 도메인 Entity 및 책임에 따른 모듈/util/handler 분리 등 사전 도메인 시스템의 가독성을 높이고 유지보수성을 향상하는데 기여할 수 있었던 귀중한 경험이었습니다.

ISSUE 02

사용자 경험 및 오류 추적성 향상을 위한 Global Exception/Exception Object Driven 체계 도입 방안

🚨 문제 인식

Finastra 프레임워크에 맞춘 장애 발생 시 사용자 경험 향상 및 오류 추적성을 확보하기 위해 공통 Checked Exception 기반의 Service 로직 구성이 필요하였습니다.

✅ 문제 접근 및 해결 방안

담보의 경우 사전에 속하면서 별도 분리된 특수 도메인으로, 사전 업무 체계에 비해 최초 서비스 로직 및 고객 메시지 처리에 대한 빠른 구성이 필요하였습니다. 특히, 사용자 경험 개선을 위한 Checked Exception 기반의 메시지 처리가 필요하였는데(프레임워크 특성상 Javascript 기반의 동작 불가), 이에 대해 맞춤형 공통 Exception 및 상속체계를 도입하여 사용자 경험을 개선하고 이를 기반으로 한 오류 추적성을 확보하는데 기여하였습니다.
다만, Checked Exception의 경우 잔여 금액 및 Human Error 등 front 요소에 적용하였고, 이 외는 모두 Unchecked Exception으로 통합하여 내부 정책적 요소(트랜잭션 진행 및 Rollback 발생 등)에 대한 원자성과 일관성을 보장할 수 있도록 구성하였습니다.
참고로 Finastra의 프레임워크가 MVC가 아닌 Service layer 단독으로 되어있는 구조라는 점, 사전 도메인에서 필요한 경우에만 사용해야 한다는 점 등 여러 제한적 특성 상 Interceptor 및 Filter보다는 별도의 Exception 체계 구축이 좀 더 현실적인 방안이라는 판단하에 Excetpion 객체 기반의 도메인 정책 예외 및 service 처리의 도입을 최종 채택, 적용하였습니다.

ISSUE 03

Xlink 기반 외부 open API 통신 시 xml 기반의 비효율성 개선 방안

🚨 문제 인식

외부 API 기반 통신 시 최초 xml 기반의 송수신 및 전문 규격의 비일치가 발생하여 상당한 비효율성이 발생하였습니다.

✅ 문제 접근 및 해결 방안

외부 협력사에서 제공하는 API의 전문 규격은 xml, Json 등 여러가지가 존재하였습니다. 그 중 Json을 규격으로 하는 협력사 API 전문이 다수를 차지하였으나, 모든 통신 service 로직이 xml 기반(혹은 하드코딩)으로 구현되어 있는 상태였고 이로 인한 전문 규격에 맞지 않은 파싱 및 복잡도 등 운영 비용 측면에서 개선이 필요하였습니다.
이를 위해 아웃바운드 통신 시JSON 기반의 요청 및 응답을 진행할 수 있도록 전문 기반을 개선하였으며, 이러한 JSON 규격의 통신을 사전 도메인에서 간편하게 구현 및 재활용할 수 있도록 handler화 하였습니다. 결과적으로 다수의 외부사 JSON 통신 규격에 맞추어 기존 일괄적인 xml 기반 통신 체계 대비 적절한 Service 로직 구현 및 간결화가 가능해졌으며, 나아가 가독성 및 유지보수성을 향상할 수 있었습니다.
참고로 소수의 xml 혹은 그 이외의 통신 방법으로 이루어지는 체계의 경우 기존 DocumentBuilderFactory/DocumentBuilder 등의 파싱 과정을 그대로 활용할 수 있었기에 각 전문 규격에 맞춘 적절한 기반을 선택할 수 있게 되었습니다. 기존 xml 파싱 체계를 그대로 유지해오던 기반을 JSON 전문 기반을 추가 및 개선하여, 외부 API 통신을 위한 service 구축 시 적절한 규격의 선택, 이를 통한 효율적인 Service 로직을 구현할 수 있었던 경험이었습니다.

ISSUE 04

사전 도메인 내에서의 기술적 의사소통 부재

🚨 문제 인식

아키텍칭 적용 및 사용자 경험 개선 등 기술적 개선 요소를 대입할때 팀 내 의사소통이 심각하게 부재하였습니다.

✅ 문제 접근 및 해결 방안

사전팀의 Finastra 프레임워크 기술부채 누적 및 세부 아키텍칭 필요성 증대 등 개인이 해결하기 힘든 수준의 이슈가 날이 가면서 누적되었으나, 의사소통 누락 및 이슈 방치로 인해 업무적으로 불필요한 비용 소모와 지연이 지속되었습니다.
같이 프로젝트에 참여한 동료분들 중 가장 경험이 부족한 신입이었지만, 당시 스쿼드 차원의 진행이 필요하다고 판단하여 직접 주간 리뷰를 주최하고 구성하는 등 적극적으로 대응 방안을 마련하고자 하였습니다. 이때 사전 도메인의 기술적 부채 감소와 세부적인 요소 아키텍칭 등 업무 효율성을 향상하기 위한 방안을 최우선적으로 고려하였으며, 최종적으로 스쿼드 수준의 개선안 공유와 적극적인 의사소통을 작게 나마 도모할 수 있었습니다.
페어 프로그래밍이나 피어 리뷰 등의 이론적인 Agile 요소도 존재하였지만, 일정이 충분하지 않고 해당 요소를 도입할 만큼의 충분한 이유, 상태, 기술적 이해도가 부족하여 당시 실무 상황에 가장 부합하는 현실적인 방책을 최대한 적용하고자 하였습니다.
